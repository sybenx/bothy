# Test notes

Notes on how this suite is laid out and why a few of its fixtures look the
way they do.

## Layout

- `test/skeleton.test.ts` — Worker/Durable Object skeleton smoke tests. Don't add protocol assertions here.
- `test/hibernation.test.ts` — the hibernation smoke test, and the rows-**written** baseline: `eventRowCost`'s derivation from `schema.ts INDEXES` asserted against real `SqlStorageCursor.rowsWritten` on the real `storeEvent` path. That pairing is the point — the figure is derived so a new index updates every consumer of it at once, and measured so the derivation cannot be quietly wrong. This project shipped a rows-written figure that was off by 45× because nobody measured it.
- `test/schema-migration.test.ts` — column/table reconciliation (`reconcileColumns`/`initSchema`) against real historical table shapes, plus `computeSchemaHash`'s two load-bearing properties: every field the reconciler acts on changes the hash, and a migration that throws partway leaves the previously stored hash untouched. Also the rows-read baseline for the schema-hash short-circuit itself — `initSchema` costing O(1) on a wake where nothing changed, versus the full reconcile pass on the wake that actually needs it — the same measure-don't-estimate discipline `hibernation.test.ts` applies to rows written.
- `test/nip01-write.test.ts` — EVENT/OK: accept, duplicate, bad signature, id/content mismatch.
- `test/nip01-subscriptions.test.ts` — REQ/EOSE/CLOSE lifecycle, real-time delivery, sub replacement.
- `test/nip01-filters.test.ts` — ids/authors/kinds/`#tag`/since/until/limit, AND-within, OR-across, ordering.
- `test/nip01-kinds.test.ts` — regular vs. replaceable vs. ephemeral vs. addressable storage rules.
- `test/nostr-kinds.test.ts` — kind-classifier boundary values (44/45, 999/1000, 9999/10000, 19999/20000, 29999/30000, 39999/40000), asserted directly against `isReplaceableKind`/`isEphemeralKind`/`isAddressableKind` rather than over the wire.
- `test/nip09-deletion.test.ts`, `test/nip40-expiration.test.ts`, `test/nip42-auth.test.ts` — one file per optional NIP.
- `test/ownership.test.ts` — owner-only write gate (fixed OWNER_PUBKEY binding).
- `test/claim.test.ts` — TOFU claim flow: HTTP behavior with OWNER_PUBKEY set, plus claim atomicity and pubkey normalization tested directly against real storage.
- `test/follows.test.ts` — ALLOW_FOLLOWS write gate, tested directly against real storage.
- `test/groups.test.ts` — the `is_group` partition, organised by SURFACE rather than by function, because that is the failure mode: an exclusion applied to REQ results is not applied to `broadcast()`, to `liveBroadcast()`, or to the counters on `/api/stats`, and each of the four has its own describe block. Also the omit-don't-refuse split (a filter naming a group is refused from the filter alone; one that does not is answered with the rows omitted, identically whether or not the group holds anything), the kind-agnostic definition — an `h` tag on any kind, asserted across six of them, since a design that leaned on a kind range would be a subset of NIP-29 rather than NIP-29 — and the cost invariant the whole thing rests on: an unauthenticated read stays flat as the group fills, measured against 5,000 seeded group rows. The one deliberate non-assertion is `rowsWrittenToday`, which still moves for a group event; that test exists to record the trade rather than to lock in a leak. See CLAUDE.md "The budget" and `src/groups.ts` for the measurements behind the partition design.
- `test/nip29-groups.test.ts` — group WRITES, and the three things this feature had to get right, one describe block each. Plus a fourth block added later, on the two write paths dispatched above BOTH gates: that an `h`-tagged gift wrap is now refused outright (it used to land in the group partition unauthorized, which is unauthenticated injection into a private feed), and that NIP-62 vanish has no equivalent hole because it stores no event at all — asserted by sending a vanish that carries an `h` tag of its own and finding nothing stored. That the relay-generated 39000-series is caught by the partition at all (it carries a `d` tag and no `h`, so the `h` rule saw nothing in the admin and member lists — the two events that enumerate the group's membership). That a relay-signed event bypasses the write GATE and not the BOOKKEEPING, asserted by running the daily counter audit — which recounts the table rather than trusting the counters — over a relay whose only events are relay-generated, so a second insert path would fail here rather than silently under-report the write budget. And what a membership change actually costs in rows written, measured on a real `SqlStorageCursor`, which makes this file part of the rows-written baseline alongside `test/hibernation.test.ts`. Also the two-nested-lists rule (put-user grants both, remove-user takes back only what the group gave, `allowpubkey` promotes), the refusal paths (a client-signed 39000-series event, an unimplemented moderation kind, a moderation event naming another group or removing the owner), and the daily membership-containment check — including that what gets STORED in `last_drift` counts members rather than naming them, since `/api/stats` reads that column back and is public.
- `test/read-limits.test.ts` — subscription cap, rejection of a filter no index can serve, per-IP throttle.
- `test/read-cost.test.ts` — rows read per query shape, before and after the v0.7.2 index/split/cache work, plus the `boundFilter` cost model and the read-path attribution buckets.
- `test/exhaustion.test.ts` — the budget-exhaustion classifier: names the resource when it can, still reports exhaustion when the wording is unfamiliar, and never classifies an ordinary bug as exhaustion.
- `test/nip62-vanish.test.ts` — also covers resumability: a vanish larger than one batch drains across ticks, keeps its checkpoint, tombstones as it goes, and widens rather than narrows if a second request names a different cutoff.
- `test/nip09-deletion.test.ts` — also covers the `a`-tag kind restriction: a coordinate naming a regular kind is ignored rather than deleting every event of that kind.
- `test/rate-limit.test.ts` — per-IP HTTP rate limiting. Asserts the *shape* rather than the number: that an allowance exists, that it is keyed by address, that it is shared across every path that wakes the Durable Object, that `/api/profile`'s is strictly tighter, and that static assets sit outside it. The limit and window are enforced by the Cloudflare runtime from `wrangler.jsonc`, so a test asserting `60` would be restating the config file rather than checking it. **The limiter is live in the test environment** — miniflare implements the binding — which is why every test there uses its own `CF-Connecting-IP`: the allowance is shared across a whole file, so two tests on one address would be one test measured twice. Existing suites are unaffected because `helpers/socket.ts` opens its WebSockets against the Durable Object stub directly, never through the Worker's router, so they never reach the limiter at all. A future test file making more than the allowance in HTTP requests through `exports.default.fetch` will start seeing `429`s; give it its own address. One trap is worth knowing before writing another: **the window is fixed, not sliding**, so a probe that straddles a rollover has its count split across two windows and never trips a limiter that is working perfectly. That made this file fail about one run in three until the probe was sized past twice the largest allowance, and it is why nothing here asserts the number of admitted requests directly — only that it is non-zero, or smaller than another endpoint's.
- `test/nip98-auth.test.ts` — also pins the *ordering* of the management gate, which is a budget property and is asserted the way the rest of the budget is: by measurement. `getOwner` is the only thing on that path that touches storage and it declares the read path `identity`, so `read-metrics.ts` can answer directly whether the Durable Object read anything on behalf of an unauthenticated POST. It must read nothing — and the positive control beside it (a stranger's *valid* signature, the cheapest request that legitimately has to ask who the owner is) exists because a metric reading zero for lack of instrumentation is indistinguishable from one reading zero because nothing happened.
- `test/stats.test.ts` — `/api/stats` shape, `/api/profile` validation and its scoping to the pre-claim window, admin page fallback, and the maintained event counters. The counter block is the interesting half: it asserts that every removal path in the relay brings the counters back down (replaceable replacement, NIP-09, NIP-86 `banevent`), that a `banevent` on an id that was never stored decrements nothing, that a backfill-aged `created_at` stays out of the 24h window while still counting toward the total, that the seed migration runs exactly once and does not recount on a later schema change, and that `auditMaintainedCounts` logs a drift and leaves it uncorrected. `test/follows.test.ts` carries the matching block for `follows`: that both of `refreshFollows`' write branches move the count, and — the assertion that pins the design — that a refresh finding an unchanged contact list writes **zero** rows, counter included, which is what says the counter write lives inside the rebuild branch rather than at the function's exit. Also the one cache left behind the endpoint: that it holds steady between requests while the maintained counters move immediately beside it, that a write-budget figure measured from a previous UTC day is discarded however fresh it looks, and that it survives eviction by being a row. The `stats_snapshot` half is gone and is asserted absent — `initSchema` drops the table — since every field it held became a counter or was deleted.
- `test/stats.test.ts` also proves `/api/profile` refuses a claimed relay's request *before reaching the network*, which the status code alone cannot: a 404 returned after opening two outbound WebSockets looks identical from the outside, and that connection is the entire cost being removed. A lookup leaves exactly one visible trace — an entry in the kind-0 cache — so `profileCacheSize()` being zero is the assertion. That and `resetProfileCache()` are test seams in `src/profile-lookup.ts`; nothing in `src/` calls either.
- `test/read-cost.test.ts` — also pins what a warm `/api/stats` load costs. Its one test that widens the seeded ingest window to every row does so inside a `try`/`finally` that restores the file's `RECENTLY_INGESTED = 10` shape: the rest of the file is written against that window, and the cost this test measures is invisible at that size.
- `test/helpers/` — shared fixtures (see below).

## Helpers

- `keys.ts` — a fixed `OWNER_SECRET_KEY_HEX`/`OWNER_PUBKEY_HEX` pair (matches the `OWNER_PUBKEY` binding injected in `vitest.config.ts`), plus `randomKeypair()` for non-owner authors.
- `event.ts` — `signEvent()` builds a correctly-signed NIP-01 event; `withCorruptSignature()`/`withTamperedContent()` build negative fixtures.
- `socket.ts` — `connectRelay()` opens the hibernation-safe WS to the singleton DO; `publish()` and `collectStored()` wrap the send/await-response pattern.
- `management.ts` — `callManagement()` sends a NIP-86 request through the Worker's fetch handler, signing the NIP-98 authorization for it. The management API is the one client path in this project that is plain HTTP rather than a WebSocket, so it does not go through `socket.ts` at all. Every field of `AuthOptions` overrides exactly one part of the authorization, so a reject-path test can break one rule at a time; the accept path is the same call with no overrides. Management calls wake the Durable Object through the same shared per-IP limiter `rate-limit.test.ts` exercises directly (index.ts `rateLimited(env.RATE_LIMIT_API, ...)`), and this one helper is shared by three test files making well over a hundred calls between them — a call that didn't ask for a particular `ip` used to send no `CF-Connecting-IP` header at all, which reads as the literal address `"unknown"`, so every unlabeled call across all three files shared one bucket. `callManagement` now assigns a fresh, sequential, private-range address (`10.x.x.x`) to any call that doesn't pass `ip` explicitly, so no amount of test growth can pool enough unlabeled calls to trip the shared allowance; a test that specifically wants a shared or particular address (the `blockip` tests) still gets one by passing `ip`.
- `isolate.ts` — `isolateStorage()` calls `reset()` in `afterEach`. **Call this at the top of every test file that writes events** — storage isolation in this vitest plugin is per file, not per test, and most files share the one owner pubkey. It used to need a second step, clearing an in-memory `/api/stats` cache that `reset()` could not reach; `/api/stats` has no cache at all now, and every figure on it is a maintained counter in storage (`maintained_counts`, `event_hour_counts`, `ingest_hour_counts`) — all for reasons that have nothing to do with tests, and `reset()` clears them with everything else. One consequence is worth knowing before writing a fixture: a test that inserts into `events` directly instead of publishing over the wire bypasses `insertEventRow` and leaves the counters behind, so assert counts against events you published, not rows you seeded. See the comment in the file itself.

## Why some things look the way they do

- Only the owner can write, so `authors`-filter tests use list membership (owner's key among others) rather than storing events from multiple authors — a second author's event can never reach storage in this relay.
- `test/read-cost.test.ts` seeds `events`/`event_tags` with direct `INSERT`s via `runInDurableObject` rather than publishing over the wire, and is the third documented exception of this kind. Its `events24h` window test extends the same exception to `event_hour_counts`, seeding five years of hourly buckets directly: the claim being measured is that the window read is bounded by the window and not by how deep the history is, and reaching five years of history through the protocol would mean five years of signatures for rows whose read cost has nothing to do with how they were written. Its subject is what a query costs at a table size where a full scan is unmistakably distinct from an index seek, and reaching that size through the protocol would mean thousands of schnorr signatures for rows whose read cost has nothing to do with how they were written.
- That file measures each cost **both ways** — the pre-v0.7.2 form and the current one, against the same rows in the same Durable Object — so CLAUDE.md "The budget"'s before/after table is a measurement rather than two runs compared from memory. Where an index is the thing that changed, the "before" case is reproduced with SQLite's unary `+` operator, which suppresses index use on a term (sqlite.org/optoverview.html), rather than by dropping and recreating the index. Dropping it would leave the shared DO in a different state for whatever test ran next; `+kind` reproduces the old query plan and touches nothing.
- One assertion there is still shaped as "this is expensive and scales with the table" rather than "this must stay under N": the `event_tags` delete. It records a measured fact that was deliberately **not** fixed — the reasoning, the arithmetic and the estimate of how often the path is hit are in the comment on `deleteEventRow` in `src/storage.ts`, beside the query they are about — and a test that pretended otherwise would hide it.
- `test/nip29-invites.test.ts` — kind-9009 create-invite and kind-9021 join request, organised around the four properties that make a bearer token safe to hand a stranger: single use, mandatory expiry, both nested lists written on redemption, and ONE refusal message for spent/expired/revoked/unknown. That last block is the one worth reading first — it asserts a `Set` of the messages has size 1 across six different refusal causes, which is the only shape that catches a helpful error string being added later. It opens a connection per attempt from its own address, because the per-IP join throttle would otherwise answer the last few itself and hide the refusal being asserted. Also a rows-written block, measured on a real `SqlStorageCursor` like `test/nip29-groups.test.ts`'s, which puts issuing (14) and redeeming (109) into the budget baseline; it drops to storage for the same harness reason noted below, and additionally for the expired-invite state, which no sequence of client frames can reach inside one run without a clock to advance.
- `test/nip40-expiration.test.ts`'s "does not return a stored event whose expiration has since passed" case inserts a row directly into the `events` table (via `runInDurableObject`) instead of going through the wire. That's the one deliberate exception to testing purely over the wire: there's no way to make an event expire *after* it was validly stored without controlling wall-clock time, and NIP-40's write-time and read-time rules are independent SHOULDs that need to be tested independently.
- NIP-42 tests cover both the AUTH message's own validation contract (kind, freshness, challenge match) and a full challenge/response round trip, because gift wrap reads are this relay's one auth-gated resource: a `kinds: [1059]` REQ is the only thing that makes it issue a challenge, so everything downstream of one — relay-tag matching, the owner being served their inbox, an authenticated stranger being refused it — has to be reached through that gate. The gate itself is then tested from two more directions because it re-runs each filter restricted to kind 1059 against real storage rather than pattern-matching the filter's shape: the filter-shape cases pin down which REQ shapes that actually gates, and the live-broadcast cases cover what it structurally cannot gate, since a filter matching no stored gift wrap registers without a challenge and every gift wrap accepted afterwards matches it.
- `test/claim.test.ts` and `test/follows.test.ts` cannot exercise the *unclaimed* relay or ALLOW_FOLLOWS=true over the wire: the global test env's OWNER_PUBKEY/ALLOW_FOLLOWS bindings (vitest.config.ts) are fixed for the whole run, matching every other suite. Instead they call the pure functions in `ownership.ts` (`claimOwner`, `getOwnerPubkey`, `isAllowedWriter`, `refreshFollows`) directly against real `SqlStorage` obtained via `runInDurableObject`, passing a hand-built `env` object rather than the injected one. This is the same category of exception `nip40-expiration.test.ts` documents for its own reason: no wire-protocol path exists to reach that state, so the test drops one level to real storage instead of mocking it.

- `test/nip86-management.test.ts`'s "still stores the value when an environment variable outranks it" case calls `handleManagementCall` directly against real `SqlStorage` with a hand-built `env`, the same exception `claim.test.ts` and `follows.test.ts` document above and for the same reason: the RELAY_NAME binding is fixed for the whole run by vitest.config.ts, so there is no wire path that reaches the state where an environment variable and a stored value are both set. Everything else about the management API is tested over real HTTP through the Worker.

- `test/nip29-groups.test.ts`'s rows-written block calls `storeEvent` and `applyModeration` directly against real `SqlStorage` rather than publishing over the wire, and this one is a harness limit rather than a state that has no wire path: `runInDurableObject` cannot drive a WebSocket belonging to another Durable Object context ("Cannot perform I/O on behalf of a different Durable Object"), and measuring `rowsWritten` means holding the storage handle while the write happens. Those two calls are exactly what `relay.ts acceptEvent` does for a moderation event once the gate has admitted it — store the event, then apply it — so the figure covers the whole write and omits only the gate checks, which are reads. Everything else in that file goes over the wire.

- `test/websocket-close.test.ts` calls `webSocketClose` on the Relay instance directly instead of closing a client socket, for the same reason the fixtures above drop below the wire: RFC 6455's reserved codes (1005/1006/1015) are equally illegal for a client to *send*, so no wire-level close can deliver one. The runtime synthesizes them when a peer disappears, and calling the handler is the only way to reproduce that.

## Running

```bash
npm run test        # all suites
npm run typecheck
npx vitest run test/nip01-filters.test.ts   # one file
```
